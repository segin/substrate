# Substrate kernel performance audit (2026-07-23)

10 perf auditors over the kernel hot paths; every finding verified for genuine hotness, real cost, and a safe fix. **44 findings, all 44 confirmed.**


**Headline:** the scheduler dispatches by an O(n_all_threads) linear scan of the whole thread registry on every context switch — the real O(1) MLFQ runqueue exists but is dead code on the dispatch path. Fixing this is the single biggest win.


## HIGH

### F01. uma_curcpu() issues an MMIO LAPIC-ID read per alloc and per free on real SMP
- **Where:** `sys/vm/uma_core.c:885`  ·  mmio-vmexit  ·  hotness: per-syscall
- **Impact:** uma_zalloc (line 885) and uma_zfree (line 1047) call uma_curcpu()->smp_get_cpu_id()->percpu_get_cpu_id()->percpu_get()->lapic_get_id(). The LAPIC-ID cache is armed ONLY on uniprocessor (sys/kern/main.c:613 gates lapic_enable_id_cache on cpu_count<=1); on real SMP the cache stays disarmed, so lapic_get_id() does an MMIO read (sys/arch/x86-common/lapic.c:436) — a vmexit under KVM — on every alloc and every free. uma_slab_lock_acquire calls smp_get_cpu_id() again, and percpu_get() then linearly scans cpus[] to map LAPIC id back to an index. This is the exact 'LAPIC-ID MMIO per-lock-op storm' pattern (documented in memory) reappearing on the allocator fast path; currently masked because APs park in hlt, but it bites the moment SMP is real.
- **Defect:** CPU identity is derived by reading the LAPIC ID register and reverse-mapping it, rather than from a cheap per-CPU location. On the highest-frequency kernel path (alloc/free) this is an MMIO/vmexit plus a linear cpus[] scan on SMP.
- **Fix:** Derive the current CPU id without MMIO: store the cpu index in a per-CPU location reachable in O(1) — e.g. at a fixed offset of the per-CPU kernel stack (mask ESP), or via a dedicated GS/segment base, or an APIC-id->index lookup table indexed directly by the raw id — and have percpu_get_cpu_id() read that. This eliminates the LAPIC MMIO and the cpus[] scan from every uma_zalloc/uma_zfree on SMP.

### F02. sched_yield() linearly scans the ENTIRE thread registry on every schedule; the O(1) runqueue is dead code
- **Where:** `sys/pm/sched.c:399`  ·  algorithmic  ·  hotness: per-context-switch
- **Impact:** O(n_all_threads) walk on every context switch, voluntary block, and timer-preemption tick, run with thread_registry_lock held (which masks local IRQs the whole time). n is ALL threads, not runnable ones — under an X session that is hundreds of mostly-BLOCKED/ZOMBIE threads, of which typically 1-3 are READY. Cost scales with total thread count on the single hottest path in the kernel, and the IRQ-masked span directly inflates interrupt latency.
- **Defect:** sched_yield() (sys/pm/sched.c:399-497) picks the next thread by walking the intrusive allthread list from rr_last, testing state/proc/affinity/vruntime on every node. It touches every thread in the system regardless of runnability. Meanwhile runqueue.c implements a genuine O(1) MLFQ (ffs64 over a 128-bit bitmap, runqueue_peek/pop) and sched_smp.c wraps it in per-CPU runqueues — but the dispatch path never calls runqueue_pop()/sched_pick_next(); grep shows sched_enqueue is reached only from sched_affinity.c and the (UP-disabled) periodic balancer. The entire O(1) scheduler is vestigial while the live path is O(n).
- **Fix:** Route dispatch through the existing runqueue: enqueue a thread when it becomes READY (wake/create/preempt-out-still-runnable), dequeue on block, and make sched_yield() pick via runqueue_peek()/ffs64 — O(1), and the pick no longer needs the registry lock at all. If a full cutover is too invasive short-term, the safe intermediate is a second intrusive list threaded only through READY/RUNNING threads (a 'runnable list') so the scan visits ~#runnable instead of #all-threads, shrinking both the walk and the IRQ-masked window by orders of magnitude under load.

### F03. Object page lookup is an O(n) linked-list scan run on every fault → O(N^2) to fault in a region
- **Where:** `sys/vm/vm_object.c:239`  ·  algorithmic  ·  hotness: per-fault
- **Impact:** Faulting an N-page anonymous/file region costs O(N^2) total pointer-chases; a 100 MiB region (~25.6k pages) in one object incurs ~hundreds of millions of cache-hostile list traversals by the time it is fully resident. Cost is paid by every process that grows a large mapping (X server heap, JIT, big malloc/mmap arenas) and gets steadily worse as the resident set of a single vm_object grows.
- **Defect:** vm_object_lookup_page() linearly walks object->pages (a plain doubly-linked list keyed by nothing) comparing p->pindex until a match. vm_fault calls it at least twice per fault: once per shadow level inside vm_fault_resolve_source() (vm_fault.c:75, reached via :259) — and on a non-resident fault it scans the ENTIRE list without finding anything — and again inside vm_object_add_page()'s stale-page guard (vm_object.c:185) when the freshly filled/COW page is inserted (vm_fault.c:340 and :363). The prefault path adds a third scan (vm_fault.c:294). Because a not-yet-resident fault always scans the full current list, the per-fault cost grows linearly with the object's resident page count, making sequential fault-in of a region quadratic.
- **Fix:** Replace the object's linear page list with a pindex-keyed lookup structure: a per-object hash table (pindex -> vm_page_t*) or a radix/splay trie (FreeBSD's vm_radix is the canonical model). vm_object_lookup_page(), vm_object_add_page()'s stale check, and vm_object_remove_page() all become O(1)/O(log n). The linked list can be retained for whole-object iteration (teardown/collapse) alongside the index, or replaced entirely. This turns region fault-in from O(N^2) to O(N).


## MEDIUM

### F04. ext2 contiguity scan re-reads the same indirect/dindirect/tindirect block once per probed block
- **Where:** `sys/fs/ext2/ext2.c:795`  ·  redundant-work  ·  hotness: per-block-io
- **Impact:** On every read() of a file larger than 12 blocks, ext2_get_blocks_extent probes up to 1024 consecutive logical blocks for a contiguous run, calling ext2_get_block_num once per probed block. For a file in the single-indirect region, each call re-issues ext2_read_block on the SAME indirect block (i_block[12]); for the double-indirect region, 2 block reads per probe; triple, 3. A 1024-block contiguous run therefore drives ~1024 (or 2048/3072) full-block device->read calls for pointer blocks that are already resident in node->indirect_buf after the first read. Each is a bio-cache hit but still a full block_size (1-4 KiB) memcpy plus hash lookup + bio_lock acquire, so a single large sequential read burns megabytes of redundant memcpy and thousands of lock ops (grep/cp/link/exec of big files, and directory scans in ext2_finddir which use the same helper).
- **Defect:** ext2_get_block_num() unconditionally calls ext2_read_block() for the indirect block on every invocation (lines 737, 745/752, 760/770/774); ext2_get_blocks_extent()'s contiguity loop (lines 794-808) calls it once for every block in the run purely to verify physical contiguity, re-fetching identical pointer blocks N-1 extra times.
- **Fix:** Cache the currently-loaded indirect/dindirect/tindirect block numbers in the ext2_node_t alongside the existing scratch buffers; in ext2_get_block_num, skip ext2_read_block when the requested pointer block equals the cached one (the data is already in indirect_buf/dindirect_buf). Better: have ext2_get_blocks_extent walk the already-loaded indirect_buf array directly for the run instead of re-entering ext2_get_block_num per block. Eliminates ~all redundant pointer-block reads on sequential reads.

### F05. ext2_alloc_node does up to three 256-entry linear scans (one pure-debug) per resolved component under a global mutex
- **Where:** `sys/fs/ext2/ext2.c:1330`  ·  redundant-work  ·  hotness: per-syscall
- **Impact:** ext2_alloc_node runs for every path component that resolves to an inode (every finddir hit, cached or not) and every readdir entry materialization, all under the single global ext2_node_cache_lock. It first runs a 256-entry 'root-pin watchdog' scan (lines 1329-1350) that exists only as a debugging band-aid, then the real 256-entry lookup scan (line 1353), then possibly a 256-entry free-slot scan. That is up to ~768 iterations under a global mutex per component, serializing all ext2 inode resolution and adding a mandatory O(cache) cost even on the common hit path.
- **Defect:** The root-pin watchdog full scan is diagnostic-only work on the hottest ext2 path; the node cache itself is an unindexed linear array searched by (fs,inode_num).
- **Fix:** Compile the root-pin watchdog scan out (or behind a debug flag) so it does not run per lookup. Index the node cache with a small hash keyed on inode_num so the lookup and free-slot search are O(1) instead of O(256), which also shrinks the global-mutex critical section.

### F06. ext2_read_inode kmalloc/kfree a full filesystem block on every inode read (lookup hot path)
- **Where:** `sys/fs/ext2/ext2.c:261`  ·  extra-copy  ·  hotness: per-syscall
- **Impact:** ext2_read_inode() kmalloc()s a block_size (1-4 KiB) buffer, reads the inode-table block into it, then kfree()s it, on every call. It is called for every finddir that resolves a name (dcache hit AND miss), every htree hit, and every stat/open, i.e. per path component. That is a heap alloc+free churn plus a full-block read/copy on the hottest metadata path, contending the kmalloc lock and thrashing the allocator during path-heavy workloads (build trees, ls -R, PATH search).
- **Defect:** The per-call transient buffer is unnecessary: inode reads always happen with a directory/inode context that already owns scratch buffers, or could use an on-stack block-sized buffer / a dedicated per-cpu scratch.
- **Fix:** Read the inode-table block through a reusable buffer (the caller's ctx->block_buf, a small per-cpu scratch page, or an on-stack buffer for the common <=4 KiB block size) instead of kmalloc/kfree per call, removing the allocator round-trip from every inode resolution.

### F07. AHCI bounces every disk transfer through a freshly-allocated+zeroed DMA buffer
- **Where:** `sys/drivers/storage/ahci/ahci.c:612`  ·  extra-copy  ·  hotness: per-block-io
- **Impact:** Every SATA read and write pays: one pmm_alloc_contiguous() buddy scan (under the PMM lock) + a full-buffer memset(0) in dma_alloc_coherent (dma.c:59) + a full-buffer memcpy + pmm_free_contiguous(). For a 128 KiB sequential read-ahead that is a 32-page contiguous allocation, 128 KiB zeroed then immediately overwritten by DMA, 128 KiB copied out, and 32 pages freed — per device I/O. Under random 512 B cache-miss reads it is a per-sector page alloc/free that serializes on the PMM lock, adding lock contention to every miss. The memset is pure waste (the DMA read overwrites it; the write memcpy overwrites it).
- **Defect:** ahci_ata_dma_cmd() calls ahci_dma_bounce_alloc()->dma_alloc_coherent() (which pmm_alloc_contiguous + memset 0) on entry and dma_free_coherent() on exit for byte_count bytes, then memcpy's between the bounce and the caller buffer (ahci.c:606-624, 641-646). This alloc/zero/copy/free happens on the hot per-block-io path for both read and write. IDE by contrast (ide_dma.c) builds a scatter PRDT directly over the caller's physical pages and never bounces or zeroes.
- **Fix:** Allocate one persistent per-port bounce buffer at ahci_port_init() sized to the max transfer (or to BLKDEV_RA_MAX so it matches the read-ahead window), and reuse it under the already-held cmd_lock — this removes the pmm_alloc_contiguous/pmm_free_contiguous and the wasted memset from every I/O, leaving only the necessary copy. Better still (matches IDE): give the AHCI command table a multi-entry PRDT and DMA directly into the caller's physically-mapped buffer via pmap_extract, eliminating the bounce copy entirely (prdtl is currently hard-wired to 1 at ahci.c:635).

### F08. IDE DMA completion wait ignores the completion IRQ and only wakes on the timer tick
- **Where:** `sys/drivers/storage/ide/ide_wait.c:233`  ·  busy-wait  ·  hotness: per-block-io
- **Impact:** The IDE IRQ handler does sched_wakeup(&ide_irq_complete[channel]) (ide.c:317), but the waiter never sleeps on that channel: ide_wait_irq_completion() loops calling ide_wait_backoff(), which sched_yield()s for the first 100 iterations then sched_sleep_until(NULL, +1 tick) (ide_wait.c:36). So the IRQ wakeup targets a channel nobody is parked on. Two costs per DMA: (1) up to a full timer tick of completion latency even though the drive signalled done immediately (caps per-channel IOPS near get_hz() in the worst case); (2) on an idle uniprocessor sched_yield returns instantly, so the first ~100 iterations busy-spin, and for dma_capable channels each iteration issues two port-I/O reads — ide_bm_status() + ATA_REG_STATUS (ide_wait.c:188-189) — i.e. a burst of ~200 port-I/O vmexits under KVM burned per transfer.
- **Defect:** ide_wait_irq_completion() (ide_wait.c:178-234) polls ide_irq_complete[channel] but blocks via ide_wait_backoff() which sleeps on NULL, so the ISR's channel-targeted sched_wakeup can never wake it directly; it also re-reads two hardware port registers every poll iteration before the timeout check.
- **Fix:** Park the waiter on the same channel the ISR wakes: replace the ide_wait_backoff()/sleep-on-NULL with sched_sleep_until(&ide_irq_complete[channel], deadline) inside the wait loop so the completion IRQ wakes it at once (mirroring the correct AHCI io_wait pattern in ahci_port_issue_cmd). Drop the per-iteration ide_bm_status()/ATA_REG_STATUS reads on the fast path — the IRQ already denotes completion; read status once after wakeup for error validation. This removes the per-DMA MMIO/port-poll burst and the up-to-one-tick latency, raising IDE DMA throughput and cutting idle-CPU burn.

### F09. spinlock_acquire issues two lapic_get_id() reads plus a stable-snapshot self-check on the hottest path; release adds a third
- **Where:** `sys/kern/spinlock.c:15`  ·  mmio-vmexit  ·  hotness: per-lock-op
- **Impact:** spinlock_acquire computes id=lapic_get_id() at line 15, then immediately calls spinlock_is_held() at line 17 which internally calls lapic_get_id() AGAIN (line 105) inside a do/while stable-snapshot loop that reads lock->locked twice + cpu_id. spinlock_release calls spinlock_is_held() as well (another lapic_get_id + snapshot loop), and spinlock_try_acquire repeats the pattern. That is 2 LAPIC reads per acquire + 1 per release = 3 per lock/unlock cycle. On the current parked-hlt UP config the lapic_id cache masks the MMIO, so today's cost is just the redundant double branch + snapshot loop. But on real SMP the cache is deliberately disarmed (lapic_enable_id_cache is UP-only), so this regresses straight back into the exact 2-3 MMIO-vmexit-per-lock storm the cache was introduced to eliminate (the documented 75%->27% sy fix) — now structurally unavoidable per acquire.
- **Defect:** The self-deadlock detector (spinlock_is_held) is invoked as a subroutine on every acquire/release, recomputing the CPU id and running a torn-read-protection loop that the caller has already effectively established. The id read at line 15 is thrown away and re-read inside is_held.
- **Fix:** Read id = lapic_get_id() exactly once per operation and inline the recursive-hold check against it: `if (lock->locked && lock->cpu_id == id) panic(...)` — no separate spinlock_is_held() call, no do/while snapshot loop on the fast path. In spinlock_release, drop the lapic_get_id entirely: the holder is by construction the current CPU, so assert on cpu_id!=0xFFFFFFFF (or compare to a single cached id) instead of re-reading the LAPIC. This halves LAPIC reads in acquire (2->1) and removes them from release on real SMP, and removes the redundant snapshot-loop work on UP.

### F10. rwlock read acquire/release probe the sleepq bucket (hash + cli + bucket lock + lookup) on every operation
- **Where:** `sys/kern/rwlock.c:47`  ·  redundant-work  ·  hotness: per-lock-op
- **Impact:** rw_rlock loops on sleepq_has_waiters(writer_chan) (line 47) and rw_runlock calls it again (line 66). Each sleepq_has_waiters recomputes the hash, does pushfl/cli, a test-and-set bucket spinlock, a hash-chain walk, then sq_unlock/popfl — an entire second lock on top of the rw->lock spinlock already held, on every read lock and unlock even when no writer is anywhere near. For read-mostly rwlocks (the common use) this doubles the synchronization cost of the fast path.
- **Defect:** To avoid a stale waiting_writers counter (A42, proc_exit yanking a parked writer), the code replaced the counter with a live sleepq probe on the hot read path. The waiting_writers field still exists in rwlock_t but is now dead (only zeroed at init, never read or updated).
- **Fix:** Resurrect waiting_writers as an accurate counter maintained under rw->lock: increment when a writer parks in rw_wlock, decrement when it wakes, AND have proc_exit's sleepq-removal path decrement it when it pulls a parked writer off the writer chan (that is the one edge A42 was guarding against). Then the read path tests rw->waiting_writers (a field in the same cache line as rw->lock, already owned) instead of taking a whole sleepq bucket lock. Removes one hashed bucket lock+walk per read lock and per read unlock.

### F11. spinlock stamps last_acquire_eip (debug-only) into the lock line on every acquire
- **Where:** `sys/kern/spinlock.c:53`  ·  cache-unfriendly  ·  hotness: per-lock-op
- **Impact:** Every spinlock_acquire and spinlock_try_acquire writes lock->last_acquire_eip = __builtin_return_address(0) purely to improve a deadlock-panic message that fires only on a bug. It is an extra store to the lock cache line on every acquire; on SMP that line is already contended and this adds write traffic with no functional benefit on the success path.
- **Defect:** last_acquire_eip is a diagnostics field (used only in the 'already held by current CPU' panic). It is written unconditionally on the hot path.
- **Fix:** Gate the last_acquire_eip write behind a SPINLOCK_DEBUG build option (or drop it to the slow/contended branch only). Low individual cost, but it is free to remove from production builds and slightly reduces per-acquire write traffic on the shared lock line.

### F12. uma_zalloc/uma_zfree walk the global slab page-hash on every fast-path op just to maintain the double-free marker byte
- **Where:** `sys/vm/uma_core.c:1016`  ·  lock-contention  ·  hotness: per-syscall
- **Impact:** Every single kmalloc AND kfree (all go through UMA_ZONE_MALLOC zones with per-CPU buckets). uma_zfree takes the global recursive uma_slab_lock (cli + spinlock) and calls uma_item_marker->uma_find_slab, walking uma_page_hash[bucket], on EVERY free (lines 1013-1030) before it even touches the lockless per-CPU bucket. uma_zalloc does the same hash walk via uma_item_marker at line 920 on every bucket hit (though only under intr_disable, not the slab lock). The whole point of the per-CPU bucket cache is O(1) lockless alloc/free; the marker machinery reintroduces a shared-structure walk + (on free) a global lock on every operation, fully serializing all frees across CPUs on real SMP and bouncing the hash cache lines.
- **Defect:** The us_freelist marker byte used for double-free detection lives in the slab header, so finding it requires resolving item->slab. Both fast paths do that via uma_find_slab (a global uma_page_hash lookup). On free this is done while holding the global recursive slab lock; on alloc it is an unlocked read of a concurrently-mutated hash (also a latent SMP correctness smell). This defeats the per-CPU cache design.
- **Fix:** For on-page zones (size<=2048, i.e. every kmem zone 16..2048 and most others) the slab header is always at page_base + 4096 - (sizeof(uma_slab_t)+uz_ipers), so item->slab is pure page arithmetic: slab = (item & ~0xFFF) + 4096 - slab_overhead — no hash, no lock. Tag slab pages with a vm_page flag (PG_SLAB) set in uma_slab_alloc so the on-page vs off-page vs large distinction is O(1). Reserve the global-hash walk only for off-page zones. This removes the global lock and hash walk from the free fast path and the unlocked walk from the alloc fast path.

### F13. kmem_stats_lock global spinlock taken twice per kmalloc and once per kfree for statistics that duplicate per-zone counters
- **Where:** `sys/vm/vm_kmem.c:101`  ·  lock-contention  ·  hotness: per-syscall
- **Impact:** kmalloc acquires the single global kmem_stats_lock (spinlock_acquire_irq = pushfl/cli + spinlock) at line 101 to bump allocs/bytes, then AGAIN at line 111 after uma_zalloc to update per-bucket stats — two separate global critical sections around one allocation. kfree takes it once (line 192). This is a kernel-wide singleton lock on the hottest allocation path: on real SMP every kmalloc/kfree on every CPU serializes here purely to increment counters, negating UMA's per-CPU design. The tracked totals largely duplicate zone->uz_allocs / uz_frees / uz_count which UMA already maintains.
- **Defect:** kmem_stats is protected by one global lock and updated on the fast path. Nothing on the fast path needs a consistent global snapshot; only kmem_get_snapshot/kmem_get_stats readers do, and those are cold (/proc, diagnostics).
- **Fix:** Replace the global-locked counters with per-CPU counter structs (indexed by cpu, updated under the intr_disable window already present in UMA) or plain atomic adds, and sum them only in kmem_get_snapshot. Better, derive total allocs/frees/outstanding from the existing per-zone uz_allocs/uz_frees at snapshot time and delete the fast-path bookkeeping entirely. Either removes the global lock (and the double acquire) from every kmalloc/kfree.

### F14. kfree() calls uma_item_size() — a redundant THIRD global-slab-lock hash walk per free — only to recover the zone it then frees to
- **Where:** `sys/vm/vm_kmem.c:187`  ·  redundant-work  ·  hotness: per-syscall
- **Impact:** On every kfree, uma_item_size(ptr) acquires the global recursive uma_slab_lock and walks uma_page_hash to turn the pointer into a size/zone index (line 187). Then kfree calls uma_zfree(kmem_zones[idx], ptr), which independently re-locates the same slab (finding above) — twice more (double-free marker lookup, and uma_find_slab in the slab slow path). So a single small free performs 2-3 full global-slab-lock acquire/release cycles and 2-3 page-hash walks. On SMP this makes kfree a global serialization point; on UP it is ~3x the necessary cli/spinlock traffic per free.
- **Defect:** The size lookup exists to route the free to the correct power-of-two zone (audit A51) and update per-bucket stats, but uma_zfree already discovers the owning slab (which carries us_zone and thus the true size). The zone determination is duplicated work.
- **Fix:** Locate the slab exactly once. Have a single internal helper return the slab (hence us_zone -> uz_size -> bucket idx) so kfree gets the zone/size and uma_zfree reuses that slab pointer instead of re-walking. With the O(1) page-arithmetic lookup from the previous finding, the size recovery becomes a couple of arithmetic ops with no lock. At minimum, pass the already-found zone into uma_zfree to eliminate its second lookup.

### F15. 48 KB UDP/RAW packet ring allocated (and freed) for every TCP socket and every accepted connection
- **Where:** `sys/net/af_inet.c:582`  ·  extra-copy  ·  hotness: per-syscall
- **Impact:** afinet_socket (line 582) and afinet_accept (line 747) unconditionally kmalloc AFI_RING_LEN * sizeof(afi_pkt_t) = 32 * ~1522 = ~48.7 KB for s->ring on EVERY socket, including SOCK_STREAM sockets that never touch the UDP/RAW ring (TCP data lives in the PCB's rxbuf). A server accepting connections pays a ~48 KB kmalloc+memset-free churn per accept() plus 48 KB of resident, cold, never-read memory per live TCP connection — pure allocator pressure and cache/TLB footprint on the connection-setup fast path.
- **Defect:** The ring is only consumed by the UDP/RAW enqueue/recvfrom paths; the SOCK_STREAM path routes entirely through tcp_recv/tcp_send against the PCB. Allocating it for stream sockets is dead weight, and afinet_accept does it for every inbound connection.
- **Fix:** Gate the ring allocation on (type == SOCK_DGRAM || type == SOCK_RAW). Leave s->ring NULL for SOCK_STREAM in both afinet_socket and afinet_accept (afi_free_sock already null-checks). Saves a 48 KB alloc/free per TCP connection and ~48 KB resident per open TCP socket.

### F16. tcp_find does a linear O(N) PCB scan (twice) per inbound segment in IRQ context
- **Where:** `sys/net/tcp.c:398`  ·  algorithmic  ·  hotness: per-packet
- **Impact:** tcp_input calls tcp_find for every inbound segment; tcp_find walks the entire g_tcp_pcbs list for the 4-tuple match and then walks it AGAIN for a LISTEN match on miss (lines 404-416), all with IRQs disabled. Cost is O(active connections) per packet. A busy localhost service or a server with hundreds of short-lived connections pays that scan on every segment (including every ACK), lengthening the IRQ-off window linearly with connection count.
- **Defect:** The file's own header comment flags this: 'Per-PCB list (linear; replace with hash once profiling shows it).' On loopback every data segment is immediately ACKed, doubling packet rate and thus scan frequency.
- **Fix:** Add a small hash table keyed on (laddr,lport,raddr,rport) for the connected-PCB lookup, with a separate short list of LISTEN PCBs keyed by lport. Insert/remove on state transitions (already done under tcp_lock). Turns the per-segment demux from O(N) into O(1), shrinking the IRQ-off critical section.

### F17. sched_wakeup_n() scans the entire registry per wakeup instead of using the hashed sleepq
- **Where:** `sys/pm/sched.c:818`  ·  algorithmic  ·  hotness: per-block-io
- **Impact:** O(n_all_threads) walk under thread_registry_lock on every sched_wakeup — i.e. every pipe write, tty input, socket rx/tx, block-I/O completion, and plain sleepq/mutex/sem wake, many from hard-IRQ context. The common case wakes 1 thread on a given channel but pays a full-registry traversal to find it, and does so from IRQ handlers, extending IRQ-off time proportional to total thread count on some of the highest-frequency paths in the kernel.
- **Defect:** sched_wakeup_n() (sys/pm/sched.c:818-862) does FOREACH_THREAD matching wait_chan==chan. The kernel already ships a hashed sleep-queue subsystem (sleepq.c, sleepq_add/sleepq_remove_thread) built precisely to make wake O(#waiters-on-chan), but the plain sched_sleep()/sched_wakeup() path parks threads only via wait_chan on the flat registry and so cannot use it for lookup.
- **Fix:** Hash wait_chan into per-bucket wait lists (or fully migrate plain sched_sleep sleepers onto the existing sleepq buckets) so sched_wakeup_n walks only the threads actually blocked on that channel. A minimal, contained version: add a small chan-hash table of blocked threads maintained at block/wake time; wakeup then traverses one short bucket instead of the global list, cutting both the work and the IRQ-masked span to O(#waiters).

### F18. sched_tick() walks the whole thread registry every timer tick to find expired sleep deadlines
- **Where:** `sys/pm/sched.c:658`  ·  per-tick-scaling  ·  hotness: per-tick
- **Impact:** O(n_all_threads) scan at HZ (100-1000/s) with thread_registry_lock held (IRQs masked) inside the timer IRQ. Because sched_sleep() now arms a ~250 ms fallback deadline on essentially every sleep (lines 619-626), most BLOCKED threads carry sleep_expiry!=0, so the per-tick scan does real comparisons on nearly every node. This is a fixed per-tick tax that grows linearly with the process/thread population and lengthens the IRQ-off window every single tick.
- **Defect:** sched_tick() (sys/pm/sched.c:658-690) does FOREACH_THREAD checking state==BLOCKED && sleep_expiry && now>=expiry. There is no earliest-deadline shortcut and no count of armed timers, so even when nothing is close to expiring the full list is traversed HZ times per second under the registry spinlock.
- **Fix:** Track the minimum armed sleep_expiry (and a count of armed timers) as threads arm/disarm deadlines; sched_tick() early-outs with a single compare when now < min_deadline or count==0, doing the full walk only on the ticks something actually expires. The algorithmic endgame is a timeout wheel / sorted timer list (bucketed by expiry) so per-tick work is O(#expiring-now) instead of O(#threads); the min-deadline early-out is the low-risk first step that removes nearly all the cost immediately.

### F19. vm_fault entry lookup falls back to an O(n) linear entry-list walk, ignoring the existing splay tree
- **Where:** `sys/vm/vm_fault.c:137`  ·  algorithmic  ·  hotness: per-fault
- **Impact:** On any fault that misses both the per-map hint and the single root node, resolution is O(nentries). A process with many mmap'd regions (shared libs, X, guard-page-split heaps — easily hundreds of entries) that faults with poor locality (random access, interleaved regions) pays a full linked-list walk per fault. This is the dominant cost for scatter-access workloads where the hint rarely hits.
- **Defect:** vm_fault open-codes entry lookup (vm_fault.c:129-147): it checks map->hint, then peeks ONLY the single map->root node, then falls back to a linear scan of the entry list (for cur = map->header->next; ...). A fully functional splay tree exists (map->root with left/right, vm_map_splay at vm_map.c:709) but vm_fault deliberately never descends it because splaying mutates the tree and the fault holds only the rw READ lock (vm_map.c:701, rw_rlock). The linear fallback is the safety compromise. But the read lock already excludes all writers (who are the only ones that rotate the tree), so the tree's left/right BST structure is stable for the duration of the fault.
- **Fix:** Add a non-mutating BST descent from map->root that follows left/right by comparing va against entry->start/end WITHOUT any splay rotation. This is safe under the read lock (no concurrent structural mutation) and turns the O(n) miss into O(tree height) — average O(log n), and never worse than the current linear walk. Use it in place of the linear for-loop fallback; keep splaying confined to the write-locked insert/remove paths where it already lives.

### F20. Every path component walks the entire mountlist under a global spinlock
- **Where:** `sys/vfs/vfs.c:710`  ·  lock-contention  ·  hotness: per-syscall
- **Impact:** Runs once per '/'-separated component of every open/stat/exec/access path resolution (D acquisitions for a D-deep path), each an O(M) TAILQ walk of every mount (root+devfs+procfs+sysfs+/dev/shm+/dev/pts+... easily 6-12 entries) under a single global spinlock vfs_mount_lock. On real SMP this fully serializes ALL path lookups system-wide on one lock; even on the current UP it is a spinlock acquire + list scan per component. The existing FS_MOUNTPOINT fast-path in vfs_cross_mountpoint is completely defeated because this (inode,mp) scan runs unconditionally for every component, mountpoint or not.
- **Defect:** vfs_lookup() (the real hot-path resolver; namei()/cache_lookup in vfs_lookup.c is only reached by the cold mount syscall) resolves each component with finddir_fs, then unconditionally takes vfs_mount_lock and iterates the whole mountlist comparing current->inode/mp against every mount's covered (ino,mp) to detect a crossing. The identical scan is duplicated in vfs_lookup_lstat() at line 793. The vast majority of components are ordinary directories that cover no mount, so this is pure overhead on the common case.
- **Fix:** Gate the mountlist walk on a cheap membership test. At mount/unmount time maintain a small hash set (or bloom) of covered (mp,inode) tuples, or stamp the covered directory's cached node with FS_MOUNTPOINT; only take vfs_mount_lock and scan when the quick test says this node might be covered. Convert vfs_mount_lock to an rwlock so the rare real scans take a read lock. This turns per-component cost from O(M)+global-spinlock into O(1) with no lock in the common case.

### F21. Foreign-personality processes resolve every absolute path twice (no negative shadow cache)
- **Where:** `sys/vfs/vfs.c:632`  ·  redundant-work  ·  hotness: per-syscall
- **Impact:** For every non-native (Linux/FreeBSD/NetBSD) process, each absolute-path lookup first builds '/perso/<name>/<path>' and does a FULL recursive vfs_lookup of it before falling back to the real path. System paths (/lib, /usr/bin, /etc, ld.so search) are not shadowed, so the shadow lookup misses every time yet pays the entire per-component finddir + mountlist-scan cost, doubling path-resolution work for all foreign binaries on every open/stat/exec.
- **Defect:** The personality-shadowing branch at the top of vfs_lookup() unconditionally attempts the /perso-prefixed path first with no memory of prior misses, so repeated lookups of unshadowed system paths repeat the full failed resolution each call.
- **Fix:** Add a small negative cache of shadow misses keyed on (perso_id, path-prefix), or resolve '/perso/<name>' once at exec and record whether a shadow tree exists / cache which top-level prefixes are shadowed; skip the speculative lookup when the prefix is known-unshadowed. Compounds with finding #1 since each avoided shadow lookup also removes a full set of per-component mountlist scans.

### F22. copyinstr calls non-inlined validate_user_addr once per byte
- **Where:** `sys/kern/subr_copy.c:152`  ·  redundant-work  ·  hotness: per-syscall
- **Impact:** Every pathname copy from userspace (namei via vfs_lookup.c, plus open/stat/exec/access/unlink/rename/mkdir/etc. through syscall.c) runs this loop. For each byte of the path it makes a real out-of-line function call to validate_user_addr (declared extern in sys/include/sys/copy.h, defined in subr_copy.c, so it does NOT inline) which performs an overflow check plus 2-3 bound comparisons. A typical 20-40 byte path pays 20-40 call+branch sequences; PATH_MAX scans pay up to 1024. Path resolution is one of the highest-frequency kernel operations during any build or shell workload.
- **Defect:** The per-byte validate_user_addr(s,1) is almost entirely redundant. Bounds only change when s crosses a page boundary or approaches KERN_BASE; within a page every byte has the same validity. Re-checking each byte re-does the whole overflow+range test and eats a function-call frame per character. The on_fault handler already catches unmapped-page faults, so the only thing the bounds check adds over the fault trap is preventing reads of kernel VA (>= KERN_BASE) that would not fault.
- **Fix:** Validate only at page transitions. Compute the current page's safe end once (min(KERN_BASE, (s|0xFFF)+1)) after a single validate of s, then scan bytes freely until s reaches that boundary, re-validating only when a new page is entered. This drops validate_user_addr calls from O(len) to O(len/4096) (usually exactly one per path) while preserving identical safety. Also mark validate_user_addr static/inline or move it to a header so it can inline.

### F23. copyin/copyout use rep movsb instead of rep movsd + byte remainder
- **Where:** `sys/kern/subr_copy.c:73`  ·  extra-copy  ·  hotness: per-syscall
- **Impact:** Called on every read(2)/write(2), uiomove segment, and 60+ other sites moving bulk user data (block-cache pages to user buffers, socket buffers, etc.). rep movsb moves one byte per microcode/emulation step. Under QEMU TCG (the correctness-baseline configuration used for testing) each rep-movs iteration is a dispatched emulation step, so a 4 KiB copyout is ~4096 steps vs ~1024 for rep movsd. That is a ~4x reduction in the emulated inner loop on every bulk I/O copy under TCG.
- **Defect:** rep movsb is the textbook modern choice ONLY because ERMS microcode makes it optimal on real hardware/KVM; under TCG there is no ERMS and it degrades to a literal byte loop. Since Substrate runs and is tested heavily under TCG, and the copy length is already known and range-validated up front, moving dword-at-a-time for the bulk and handling the <4-byte tail with movsb costs nothing in correctness.
- **Fix:** In the asm, when size>=4 do 'mov %ecx,%edx; shr $2,%ecx; rep movsl; mov %edx,%ecx; and $3,%ecx; rep movsb' (single cld, single on_fault arm/disarm still covering the whole sequence). The fault label already handles a trap anywhere in the rep sequence. Net: identical semantics, ~4x fewer emulated iterations under TCG; no regression under KVM.

### F24. memmove always copies byte-at-a-time even for non-overlapping regions
- **Where:** `sys/lib/string.c:51`  ·  algorithmic  ·  hotness: per-syscall
- **Impact:** memmove never uses the word-at-a-time path that memcpy has; every call is a pure byte loop regardless of size or alignment. Callers use memmove defensively (possible overlap) but the overwhelmingly common runtime case is disjoint buffers, which could run at memcpy speed. For large moves (buffer-cache shuffles, tty/line-discipline buffer compaction, string builders) this is 4x-8x slower than necessary.
- **Defect:** When the source and destination ranges do not actually overlap, a forward memcpy is correct and much faster. Only genuinely overlapping backward-direction moves need the byte loop. The current code takes the slow path unconditionally.
- **Fix:** Add a disjoint-range test at entry: if (d+n <= s || s+n <= d) return memcpy(dest,src,n); Only fall through to the byte-wise forward/backward loops when the ranges truly overlap. This reuses the already-optimized memcpy word path for the common case with a two-comparison guard.

### F25. mutex_unlock unconditionally takes the guard spinlock AND probes the sleepq on every unlock, even fully uncontended
- **Where:** `sys/kern/mutex.c:112`  ·  redundant-work  ·  hotness: per-lock-op
- **Impact:** Paid on essentially every kernel critical-section exit (mutex_unlock is used across vfs/net/vm/kern). The lock fast path is a single lock-free CAS (mutex_trylock), but the unlock path is wildly asymmetric: every uncontended unlock does spinlock_acquire(&m->guard) + sleepq_wake_one(m) + spinlock_release(&m->guard). sleepq_wake_one alone recomputes the channel hash, does pushfl/cli, a test-and-set bucket lock, a hash-chain lookup that almost always finds nothing, then sq_unlock/popfl — all to discover there are zero waiters, which is the common case. Plus spinlock_acquire/release each drag in lapic_get_id and the snapshot self-check (finding below). So the cheap-to-take mutex is expensive to release.
- **Defect:** mutex_unlock (line 115) always grabs m->guard and then calls sleepq_wake_one(m) at line 132 with no waiter check. The overwhelmingly common case is an uncontended mutex with an empty sleepq, yet it still performs two full spinlock round-trips and one hashed sleepq bucket lock+lookup.
- **Fix:** Track contention explicitly: add a `contested` byte to mutex_t, set (under m->guard) in the slow path right before/after sleepq_add() when a thread parks. Uncontended unlock becomes guard-free and probe-free: verify owner, mutex_untrack_owner, m->owner=NULL, __sync_lock_release(&m->locked); only if `contested` is set do you take m->guard and call sleepq_wake_one (clearing the flag when the queue drains). This turns the common unlock from two spinlock acquisitions + a bucket lock into a couple of plain atomic stores. Mirror the same pattern in sema_post (semaphore.c:32), which likewise calls sleepq_wake_one whenever value>0 regardless of whether any waiter exists.

### F26. memtrack takes a global lock + does a hash probe on every physical page alloc and free
- **Where:** `sys/arch/i386/pmm.c:1051`  ·  lock-contention  ·  hotness: per-fault
- **Impact:** pmm_alloc_block (line 1051), pmm_alloc_contiguous, pmm_free_block and pmm_free_contiguous each call memtrack_record_alloc/free, which acquires the global memtrack_lock (spinlock_acquire_irq) and runs a linear-probe hash over MEMTRACK_SITES keyed on the caller PC (sys/kern/memtrack.c:27-44). This is on the per-page-fault and per-slab-refill path. On real SMP it serializes all physical allocation on one lock; on UP it adds a cli/spinlock + hash probe (plus a __builtin_return_address read) to every page alloc/free. pmm_alloc_contiguous even loops the per-frame stamping under the accounting.
- **Defect:** memtrack is always-on accounting (per CLAUDE.md tripwires). Its per-site aggregation is protected by a single global lock taken on the hottest MI page path.
- **Fix:** Accumulate per-CPU (per-site, per-CPU counter arrays) and merge only when /proc/memtrack or sys_vm_slabs reads, or use atomic add on the site's pages_alloc/pages_free with a lock-free lookup (the site slot is stable once assigned). ### F27. UMA full/empty bucket depot is a single global list+lock shared across all zones, with a linear zone scan on refill
- **Where:** `sys/vm/uma_core.c:239`  ·  lock-contention  ·  hotness: per-syscall
- **Impact:** When a CPU's alloc bucket empties (every ~UMA_CACHE_BUCKET_SIZE=64 allocs) uma_bucket_take_full walks the single global uma_bucket_full_depot list under the one global uma_bucket_depot_lock looking for a bucket whose ub_zone matches (lines 245-257); uma_bucket_put_full/put_empty/detach share the same global list and lock. All zones contend on one lock and one list, and take_full is O(depot length) scanning past other zones' buckets. On SMP this couples unrelated zones and adds a linear scan to every bucket refill/drain.

### F28. TCP rx ring copied byte-at-a-time in both directions (IRQ enqueue + recv drain)
- **Where:** `sys/net/tcp.c:592`  ·  extra-copy  ·  hotness: per-packet
- **Impact:** Every inbound TCP segment's payload (up to 1460 B) is copied into rxbuf with a per-byte load/store/increment/wrap loop in hard-IRQ context (tcp_in_established, lines 592-595); every tcp_recv_nb (1031-1034) and tcp_peek_nb (1088-1090) copies back out the same way. For a bulk localhost transfer this is ~1460 single-byte iterations per segment on the RX-interrupt path AND per recv() — roughly 4-8x the cost of a word-wide memcpy. - **Defect:** pipe.c and af_unix.c both explicitly replaced exactly this pattern with a two-memcpy wrap (see afbuf_read/afbuf_write and the pipe ring), but tcp.c was left on the naive byte loop. ### F29. tcp_xmit_raw bounces the segment payload through a 1.5 KB stack buffer on every (re)transmit
- **Where:** `sys/net/tcp.c:188`  ·  extra-copy  ·  hotness: per-packet
- **Impact:** tcp_xmit_raw declares buf[TCP_MSS + sizeof(tcphdr)] (~1484 B) on the stack and memcpy's seg->data into it after the header (line 188) for every transmit and every retransmit. The bytes were already copied user->seg->data in tcp_xmit_queue; this is a second full-payload copy per segment, plus ip4_output copies again into the IP packet and eth_send again into the frame. ### F31. Loopback frame copied twice per delivery (xmit into ring, drain into scratch)

### F32. THIS_CPU()/percpu_get_cpu_id() lack the UP short-circuit and issue LAPIC MMIO + linear scan on SMP per context switch

ITIMER_VIRTUAL/PROF are already serviced off current_process only (lines 1143/1147), so the loop exists solely to advance ITIMER_REAL and POSIX per-process timers — both of which already have per-process armed indicators. The overwhelming common case is that zero processes have an armed real/POSIX timer, yet the whole allproc list is still traversed every tick.
- **Fix:** Maintain a global count of processes that have an armed ITIMER_REAL or any armed POSIX timer, incremented/decremented at the arm/disarm sites (kern_setitimer ITIMER_REAL, kern_timer_settime arm/disarm, proc_timers_cancel/proc_ptimers_clear). If the count is 0, skip the FOREACH_PROC entirely. Full fix: thread an intrusive doubly-linked 'timer-active' process list updated at those same sites and walk only that list, making the tick O(k) in armed timers instead of O(n) in processes. Serialize the list under the existing pid/proctree lock for SMP correctness.

### F39. sched_tick walks every thread and takes the registry lock on every tick
- **Where:** `sys/pm/sched.c:667`  ·  per-tick-scaling  ·  hotness: per-tick
- **Impact:** O(nthreads) traversal plus one tid_lock acquire/release every HZ tick, purely to find threads whose sleep_expiry has elapsed. Threads typically outnumber processes, so this is the larger of the two per-tick walks. The unconditional lock acquire also issues lapic_get_id ownership stamping (MMIO/vmexit on real SMP) once per tick, and serializes the tick against every sleep/wake.
- **Defect:** sched_tick() does `thread_registry_lock(); FOREACH_THREAD(thread){ if BLOCKED && sleep_expiry>0 && now>=sleep_expiry -> wake }`. The vast majority of ticks expire nothing, but the lock is taken and the entire thread registry scanned regardless.
- **Fix:** Track the global minimum armed sleep_expiry across timed sleepers (updated when a thread arms a timed sleep, recomputed lazily on wake) and/or a count of timed sleepers. sched_tick reads that scalar locklessly and returns before taking tid_lock or walking when now < min_expiry (or count==0). This makes the no-expiry common case O(1) with no lock. A bucketed timer wheel keyed by expiry tick is the complete algorithmic fix, giving O(expired) work.

### F40. gettimeofday/clock_gettime do 64-bit ticks/HZ and ticks%HZ divides when the values are already maintained
- **Where:** `sys/kern/time.c:398`  ·  redundant-work  ·  hotness: per-syscall
- **Impact:** HZ is 250 (not a power of two), so `ticks / HZ` and `ticks % HZ` on the 64-bit tick counter compile to __udivdi3/__umoddi3 (~70-100 cycles each on i386). kern_gettimeofday and kern_clock_gettime each do two of these per call. gettimeofday/clock_gettime are hot (X server socket writes, ping, poll timeouts), so this is a recurring software-division cost on a frequently-called syscall.
- **Defect:** kern_gettimeofday computes `boot_time + (ticks/HZ)` and `((ticks % HZ)*1e6)/HZ` (lines 398-399); kern_clock_gettime repeats the pattern at lines 465/467/474. But the tick handler already maintains uptime_secs (== ticks/HZ) and tick_in_sec (== ticks%HZ, a uint32) incrementally at lines 1114 precisely to avoid this divide (see the get_time() comment at top of file), yet these two syscalls don't use them.
- **Fix:** Read uptime_secs and tick_in_sec (under intr_disable for a consistent pair) instead of dividing the raw tick counter: seconds = boot_time + uptime_secs, and sub-second = (tick_in_sec * 1000000)/HZ — the latter is now a 32-bit divide of a value < HZ*1e6. Eliminates both 64-bit divide/modulo per gettimeofday/clock_gettime call.

### F41. sched_vruntime_tick does a 64-bit divide on every tick
- **Where:** `sys/pm/sched.c:48`  ·  redundant-work  ·  hotness: per-tick
- **Impact:** `((uint64_t)NICE_0_WEIGHT << VRUNTIME_SHIFT) / w` is a __udivdi3 executed on every tick for the running timeshare thread (called from isr_handler each timer IRQ). The dividend and w are constant between priority changes, so the divide result is invariant yet recomputed every tick.
- **Defect:** The per-thread vruntime increment depends only on the thread's weight w (derived from base_priority). w changes only on renice/priority change, but the tick recomputes the full 64-bit division each time.
- **Fix:** Precompute and cache a per-thread vruntime_step = (NICE_0_WEIGHT<<VRUNTIME_SHIFT)/w whenever base_priority/weight is set, and have sched_vruntime_tick just do `t->vruntime += t->vruntime_step`. Removes the software divide from the per-tick path.

### F42. proc_ptimers_fire recomputes 'now' (rdtsc + divide) per armed timer instead of once per clock domain
- **Where:** `sys/kern/time.c:870`  ·  redundant-work  ·  hotness: per-tick
- **Impact:** For each used+armed POSIX timer, ptimer_now_ns() calls kern_clock_gettime() which does an rdtsc-based subtick_nsec() (a 64-bit divide) plus the ticks/HZ math. A process with several armed timers repeats this identical per-domain 'now' computation once per timer per tick. Only paid when timers are armed, so bounded, but redundant.
- **Defect:** The loop over POSIX_TIMER_MAX calls ptimer_now_ns(clockid) inside the loop body; within a single tick the monotonic and realtime 'now' are effectively constant, so computing them per timer wastes rdtsc reads and divides.
- **Fix:** Compute now_mono and now_real once at proc_ptimers_fire entry (lazily — only the domain(s) actually referenced by an armed timer) and reuse the cached values across the timer loop instead of calling ptimer_now_ns per iteration.

### F43. A single global mutex serializes every page fault system-wide
- **Where:** `sys/vm/vm_fault.c:180`  ·  lock-contention  ·  hotness: per-fault
- **Impact:** On the current effectively-UP kernel this is only a mutex lock/unlock pair per fault (small, constant). On real SMP it is a hard scalability wall: every faulting CPU serializes on one lock through the entire object-resolve + pager-fill + COW + pmap_enter region, so N cores fault no faster than one. Fault-heavy parallel workloads (parallel make, multi-threaded servers) would see near-zero fault throughput scaling.
- **Defect:** vm_fault_object_lock_acquire() (vm_fault.c:31, taken at :180) takes one process-global mutex (vm_fault_object_lock) across the whole resolve/fill/COW/pmap_enter body of every fault. The header comment acknowledges it is 'coarse but provably deadlock-free' and that per-object locking is future work. It is correct, but it means concurrent faults on unrelated address spaces / unrelated objects cannot proceed in parallel.
- **Fix:** Move to per-vm_object locking (a lock embedded in vm_object, taken in a fixed order down the shadow chain) so faults on distinct objects run concurrently. This is a bigger change and only pays off once APs actually schedule, so it is correctly deprioritized relative to the O(N^2) algorithmic fixes — but it is the structural fix needed before SMP fault scaling is real.

### F44. pmap_protect walks the range a second time just to issue INVLPGs
- **Where:** `sys/arch/i386/pmap.c:1639`  ·  redundant-work  ·  hotness: per-syscall
- **Impact:** An mprotect over an M-page range that stays under TLB_BATCH_THRESHOLD (32) re-walks the page tables a second full time (re-deriving V_PD[pdi]/V_PT and re-testing PTE_P per page) purely to call pmap_invalidate_page. Doubles the page-table traversal work of every small mprotect and of COW-downgrade paths that funnel through pmap_protect.
- **Defect:** After the main loop updates PTEs and records first_va/last_va/pages_modified, the small-range branch (pmap.c:1639) loops again from first_va to last_va, re-reading V_PD[pdi] and V_PT(pdi)[pti] and re-checking PTE_P before each INVLPG. The main loop already knows exactly which VAs it touched.
- **Fix:** Issue pmap_invalidate_page(va) inline inside the main loop right after writing pt[pti] for the small-range case (or record touched VAs in a small stack array during the first pass), eliminating the second walk. Keep the CR3-reload full-flush for the >THRESHOLD case. Minor, but it halves the work of the common small-mprotect / COW-downgrade path.
