# Architecture Overview

This document is the living architecture baseline for the Substrate native C compiler in `usr.bin/cc/`.
It explains how the compiler is partitioned into driver, frontend, middle-end, and backend stages, and how those stages interact with the in-tree assembler and linker.

## 2. High-Level System Diagram

```text
C Source
  -> preprocessing
  -> lex / parse / sema
  -> AST -> SSA IR
  -> optimization + legalization
  -> instruction selection / regalloc / frame lowering
  -> GAS-style assembly (.s)
  -> as
  -> ELF object (.o)
  -> ld
  -> executable / shared object

Driver control plane:
  cc resolves sibling tools first (../as/as, ../ld/ld),
  then falls back to PATH tools or explicit environment overrides.
```

## 3. Core Components

### 3.1. Driver And Toolchain Orchestration

Name: `cmd/cc.c` and `cmd/pipeline.c`

Description: The driver parses user-facing flags, chooses stage stop points (`-E`, `-S`, `-c`, full link), resolves companion tools, and coordinates subprocess execution. It is the boundary between pure compilation logic and host/target toolchain integration.

Technologies: C, fork/exec, argument-vector construction, mode-aware tool resolution

Deployment: Installed as `usr/bin/cc`; `cpp` is exposed as a symlink to the same binary

### 3.2. Frontend

Name: Preprocessor, lexer, parser, and semantic analysis

Description: The frontend turns C translation units into typed ASTs. Diagnostics name the file a construct is in as gcc does: the preprocessor writes gcc's line markers, `# 1 "hdr/s.h" 1` (the file as included, `pp_include_display()`; flag 1 entering it, 2 back in its includer), the lexer keeps the files they name in the translation unit's table (`cc_src_files_t`, each with its includer and the #include's line) and each token's index in it, statements, globals, functions and calls record it (`src_file`), and the parser and sema report an error under that file after gcc's "In file included from" lines (`cc_src_files_include_chain()`, `cc_diag_t.includes`) and its "In function 'f':" or "At top level:" line, printed when the function reported in changes (`cc_diag_t.function`, `cc_diag_context()`; the parser's, sema's and the code generator's errors, and the warnings). An expression has gcc's place for its diagnostics: an identifier its own, an operator's (binary, assignment, unary `*` and `&`, `.`, `->`, a subscript's `[`) its operator token (`expr_at()`), and sema's `check_expr()` gives an operand's place back to the enclosing expression when the operand checks clean. `frontend/preproc.c` enforces macro-expansion bounds, `frontend/parser.c` owns recursive-descent parsing (the semantics C needs during parsing -- which names are variables, the type `typeof` names, the value of an array bound, enumerator or case label -- are `frontend/parse_sema.c`'s, behind `include/cc_parser.h`; trigraphs are the preprocessor's alone).  An initializer list is read as written, designations kept, and `parser_canon_initializer()` puts it, with the type it initializes in hand, in one form: every designator resolved, every elided brace restored, every aggregate a positional list of its parts and a union's list its one member's initializer; that form, and the bound it gives an array of unknown bound, is all sema and lowering see.  Then `frontend/sema.c` applies type and language rules before lowering begins: it records every expression's type, makes every implicit arithmetic conversion an explicit cast (operands, `?:` arms, assignments, initializers, returns, arguments and their default promotions), and folds every `sizeof` whose size is known, so lowering reads types and conversions and never works them out. `frontend/types.c` is the one place the size and alignment of a scalar type are decided, from the target description in `common/target.c` (`cc_target_select()` in the pipeline picks it; the same file has gcc's -march table, each CPU's level, extensions and macros, `cc_arch_find()`, and gcc's rules for the extensions' -m<ext> and -mno-<ext>, `cc_isa_from_flags()`, which the driver and the preprocessor both settle the instruction set by); structure layout, `sizeof`, `_Alignof`, lowering and the emitter all ask it. A defined enumeration's canonical type is the integer type gcc makes it compatible with (`enum_compatible_kind()` in the parser: `unsigned int` with no negative value, `int` with one, (unsigned) `long`, or `long long` on i386, beyond 32 bits; the smallest that fits when packed; the size a `mode` attribute names), so its size, signedness, promotion and compatibility are that type's -- Linux's `max()` of an `unsigned int` and an enumeration plus one checks their signedness agree; only an enumeration named before its definition is CC_CT_ENUM, which a redeclaration with the type the definition gave agrees with (`sema_same_type()`). `frontend/consteval.c` evaluates integer constant expressions (array bounds, enumerators, case labels, `_Static_assert`, static initializers) for the parser, sema and lowering alike; the parser and sema each supply the size of a `sizeof` operand as they know it, and lowering, which sees only folded ones, supplies none; each supplies the size of a type too (`type_bytes`, by its structure table), which an element's address in an array of structures, `&((T *)0)->arr[2].m`, is scaled by. `frontend/nested.c` says what a GNU nested function sees of the function it is defined in (sema puts those variables in an outer scope; lowering passes an array of their addresses in the static chain register, `%r10` or `%ecx`, when the nested function uses them, and its address is a trampoline built in the caller's frame). Names are found by index, never by walking every declaration: `frontend/nameindex.c` keeps the translation unit's functions and file-scope objects by name, built as they are looked up (the parser only appends to them), `frontend/parse_sema.c` the parser's variables in scope, kept as its scope stack is pushed and popped, and the optimizer (`middle/passes/opt.c`) and the emitter their own maps of the module's functions and globals -- a file of Linux's thousands of declarations was otherwise most of the compile. `frontend/decimal.c` reads decimal floating constants and encodes them in BID, gcc's encoding on x86, for the parser's literals and sema's constant conversions; the decimal types themselves are structures holding that encoding, operated on by libgcc's `__bid_*` functions. `frontend/binary128.c` does the same for `_Float128` (`__float128`), IEEE binary128 on both targets: it encodes constants from their text, from integers and from binary floating constants, rounded once, and folds `+ - * /` on them as gcc does; the type is a structure holding the encoding (`cc_struct_def_t.binary_bits`), passed as gcc passes it and operated on by libgcc's soft-fp (`__addtf3`, `__extenddftf2`, `__fixtfdi` and kin), sema's decimal functions handing it to its own rules.

Technologies: C, recursive-descent parsing, bounded macro expansion, semantic diagnostics

Deployment: Linked directly into the `cc` binary

### 3.3. Middle-End And SSA Infrastructure

Name: AST-to-IR lowering, legalization, optimization, and shared SSA utilities

Description: `middle/ast2ir.c` lowers the frontend AST into the compiler's SSA-like IR, one function per expression kind (`lower_expr()` dispatches; on x86-64, without -fwrapv, an add, subtract or multiply of signed ints converted to int -- an int variable's `++` and `--` among them -- is marked `nsw`, `cc_ssa_instr_t.nsw`, as its overflow is undefined: a licence for the back end to drop the extension after it, which the text form leaves out and a pass may lose; and a load through an lvalue neither volatile nor atomic, nor part of an object that is, `plain`, `cc_ssa_instr_t.plain` (`lvalue_plain()`), a licence for `opt.c`'s `cse_loads()` to read it as an earlier load of the same address with nothing between that may write it, or as the value a store there left -- to a slot, a global or through any pointer -- which the text form leaves out too); a call is `middle/lower_call.c`'s, which expands the builtins the compiler implements itself (`lower_builtin_call()`; a `__builtin_memcpy`, `__builtin_memmove` or `__builtin_memset` of a constant size up to a few words is its loads and stores, no call, as gcc makes it; an atomic read-modify-write builtin, `__sync_fetch_and_add()` to `__atomic_exchange_n()`, is one locked instruction -- `lock xadd`, `xchg`, `lock cmpxchg`, or a `lock cmpxchg` loop where there is none, `lock cmpxchg8b` for a 64-bit object on i386 -- written as the inline asm the IR already carries, or, on an i386 -march without the instruction (cmpxchg and xadd came with the 486, cmpxchg8b with the Pentium), gcc's call of `__sync_<op>_<N>` or `__atomic_<op>_<N>` (`emit_atomic_libcall()`); an assignment to an `_Atomic` object (sema's `atomic_access`; `++`/`--` on one sema makes the compound assignment it is) is `lower_atomic_assign()`'s: the address made once, a plain one stored by `lower_atomic_store_bits()`, a compound one a loop of `lower_atomic_cas_bits()` whose `x op v` is lowered with the value read and v substituted for their expressions (`lower_ctx_t.subst_expr`), and a read of one wider than a word is `lower_atomic_read()`'s one access; gcc's generic builtins, which its `<stdatomic.h>` is written in (`__atomic_load` (p, ret, mo) and the like, `cc_builtin_atomic_generic()`), are `lower_atomic_generic()`'s, the same three operations with plain accesses of the values pointed to; an 8-byte `__atomic_load_n` or `__atomic_store_n` on i386 is one access, the x87's fildq and fistpq (`emit_atomic_x87_move8()`), or before the Pentium `__atomic_load_8` or `__atomic_store_8`, `emit_atomic_asm()`, never a load and a store) and makes ordinary calls (`lower_call_expr()`). `include/cc_lower.h` holds what the two share. Lowering does not decide how an aggregate crosses a call -- to a declared function by its prototype, through a pointer by the prototype of the type pointed to, as gcc passes it: it asks the selected target (`cc_abi_aggregate_arg()`, `cc_abi_aggregate_return()` in `include/cc_abi.h`, the descriptor's hooks), and `middle/abi_x86_64.c` (the psABI eightbyte classification) or `middle/abi_i386.c` (the stack, with gcc's vector registers) answers with the ABI byte the emitters act on; `va_arg` is theirs too (`cc_abi_va_arg()`), built with `middle/irbuild.c`, the IR builder lowering also uses. The trampoline a nested function's address needs, the full fence, the va_list record `va_copy` duplicates (x86-64's va_list is gcc's, an array of one 24-byte `struct __va_list_tag`, `parser_va_list_ctype()`: an object of it is the record, which `va_start` and `va_copy` fill by a copy and `va_arg` changes in place, a parameter of it a pointer to one; i386's a pointer) and which returned aggregates the emitter reads through their address are descriptor data, so lowering never asks which target it is compiling for. On i386 under -mno-80387 (where the x87, not SSE, would do the doubles), `middle/softfloat_i386.c` runs first on each function, before the rest of legalization: every floating operation becomes a call of libgcc's soft-float routines (`__adddf3`, `__ltdf2`, `__fixdfdi`, `__extendsfdf2`, ...; a conversion to an integer narrower than 64 bits the 32-bit `__fix*si` or `__fixuns*si` gcc calls, by the signedness lowering notes on it, `cc_ssa_instr_t.f2i_to`, else the 64-bit one's low bits), a double (and a float, held as one) the 8 bytes of its bits, and a long double the address of a frame slot of its 12, passed to the routines as a structure by value and returned in `%eax:%edx:%ecx` (`CC_ABI_RET_EAX_EDX` of 12 bytes); calls, parameters and results follow gcc's -mno-80387 ABI, and sema evaluates each operation in its type (FLT_EVAL_METHOD 0), so the backend sees no floating value; a `_Float16` load or store is a call of `__extendhfdf2` or `__truncdfhf2`, the half's bits pushed and returned in `%xmm0` (taken into a frame slot as a `CC_ABI_RET_VEC128` result), with SSE2 only, as gcc; and a half parameter, argument or result as gcc passes it, its bits in a word (`sf_half_bits()`, `SF_FIX_HALF`) and a result's in `%xmm0`, a returned one's slot given back as a vector; an asm's floating register operand is its bits, a float's word and a double's pair (`sf_rewrite_asm()`), an x87 or SSE constraint refused. Where SSE does the doubles under -mno-80387 (`CC_SOFTFLOAT_LDOUBLE`) only long doubles are rewritten so, and of the floats and doubles, which SSE keeps, the conversions from and to a 64-bit integer and an unsigned int (`__floatdidf`, `__fixdfdi`, `__floatunsidf`, ...); the MIR path makes the other conversions there `cvtsi2sdl` and `cvttsd2sil` (`mir_fp.c`, by the F2I's `f2i_to`), not the x87's `fild` and `fistp`, and their results cross as below. Under -mno-fp-ret-in-387 alone the same pass (`cc_softfloat_i386_mode()`, `CC_SOFTFLOAT_RETURNS`) leaves every value to the x87 and moves only the results to that ABI: a function's floating result and a call's go through a frame slot, stored at the size returned and loaded as its words (or, for a long double, returned from the slot's address as `CC_ABI_RET_EAX_EDX`), and back. After the shared legalization, the target's own runs (the descriptor's `legalize` hook): on i386, `middle/legalize_i386.c` turns every 64-bit integer operation into operations on its 32-bit words (`lo32`, `hi32`, `pair`, `umulw`, legal IR only) and 64-bit division into a shift for a constant power-of-two divisor and `__divdi3`/`__udivdi3` calls otherwise, so the i386 emitter selects word instructions and only moves 64-bit values. Legalization runs before the optimizer, so `opt.c` runs the target's hook once more at the end of a function's passes: a call whose divisor it has since found constant (a local holding it, as Linux's `roundup()` writes) is made the shift or one 32-bit division then, since Linux does not link libgcc. `middle/legalize.c` and `middle/passes/opt.c` normalize and optimize that IR so backend selection runs on constrained, verifiable input; from -O1, `opt.c` also inlines small static inline functions bottom-up over the call graph (`middle/passes/inline.c`; one declared inline but not always_inline only where its body costs about a call's, `INLINE_MAX_COST`, where it has one caller, or where a copy of it with the call's constant arguments bound, folded on its own (`cc_optimize_function()`), does -- `rol64()` by a constant one shld -- as `inline` is a hint gcc weighs too, `hint_folds_to_small()`, or where the call passes the address of a local only such calls take, up to gcc's max-inline-insns-single, `takes_local_slot()`, the calls such a body brings in weighed again in the caller -- Linux's page-table walkers hand their on-stack `struct pt_state` to `pt_range_to_index(&pts)`; a call through a pointer inlining has made a function's address weighed as a call of that function, `calli_target()`, structures by value among its arguments, which lowering passes through a prototyped pointer as to a function declared so; past `CALLER_MAX_INSTRS` an always_inline function is inlined as a copy folded with the call's constants and the module's const tables, when that copy is small, `bound_copy()`, and so is one weighed again, in the rounds after the first -- among the call's constants a structure by value whose bytes the caller holds known, from stores of constants, of loads from const tables, or copies of them (`cc_module_slot_const_bytes()`, Linux's `raw_cpuid_get(cpuid)` in kvm_initialize_cpu_caps()); the slots such bodies keep in memory because their address escapes are shared by the bodies inlined in one round, one STACKALLOC at the entry each (`pool_bind()`), as gcc shares the frames of sibling inlined bodies) and folds again, so a call guarded by a helper that is constant in the build goes with its dead branch, as with gcc; last of all, once every function's passes are done, a static function or object nothing kept refers to is dropped, transitively (`remove_unreferenced()`: a walk from what has external linkage, is marked used, a constructor or a destructor, along each kept function's calls, addresses, loads, stores (an asm statement's operands among them; the text of an asm, a template or a file-scope one, keeps nothing, as gcc, so an instruction's mnemonic does not keep a static inline helper of that name, as Linux's `wrmsr()` was kept in its boot code) and used static locals and each kept object's initializer and alias target; from -O1 every static, at -O0 only a static inline function and the block-scope statics of the functions dropped, as gcc; a section attribute keeps nothing, as with gcc), so a static driver table whose address only an inlined call's unread argument took goes with the probe function it names and that one's calls (Linux's lm75 left `i3c_device_match_id()` undefined), and debug information, which describes only what is still defined, goes with it; a load from a const table at an offset that has become constant is the table's initializer's bytes (`fold_const_loads()`), or, of a pointer's size where the initializer puts an address -- the object itself, a member, an element -- that address, a string literal's or a symbol's, its offset an add after it (`const_address_load()`, `add_offsets()`; x86-64 reaches a symbol bound elsewhere through the GOT, whose entry is the symbol's), so the object, read nowhere else, goes too (Linux's zstd in the PIE decompressor read `static const char *const notErrorCode = "..."` from .data.rel.ro.local, a dynamic relocation the link asserts there are none of), read through a local the table's element was copied to whole, which nothing else writes, too, or a local copied in turn from such a one, as i386 passes a structure by value (`fold_const_copies()`, Linux's `pack_fields()` checks; `mem.c`'s `forward_const_bytes()` follows the bytes of locals stored constants and copied whole, through a move of the address too, under an asm goto, and a structure passed by value is a read of its local; `drop_unread_slots()` drops a whole copy into a local nothing reads), as a load from a string literal at a constant offset is the literal's byte (`literal_load()`, `"..."[sizeof("...") - 2]`), and a pointer such a table holds to a string literal or to a function or object the module defines is not null (`table_pointer_nonnull()`); a `__builtin_constant_p` lowering cannot fold, of an integer argument without side effects (`cc_constant_p_deferrable()`), is from -O1 the argument's value and a `CC_SSA_ISCONST` of it (`lower_constant_p_late()`; the parser keeps the call, which a constant expression -- an initializer, an array bound, `__builtin_choose_expr`'s condition -- takes as 0, and lowering's constant evaluator, `cc_const_env_t.defer_constant_p`, leaves undecided), which folding makes 1 wherever it knows the operand -- a local's constant initializer, an inlined function's constant argument, as Linux's `clamp()` asks it -- and `resolve_isconst()` makes 0 once inlining, constant propagation and range folding are done (`middle/passes/range.c`, which `opt.c`'s `fold_module_ranges()` runs over each function once, callers first, a static function only direct calls reach knowing its parameters within what those calls pass, so that a range passed on through parameters reaches the last callee, as gcc's interprocedural range propagation), folding the function again, so no backend sees one; `middle/passes/mem.c` follows the function's own stack slots whose addresses do not escape (a local copied whole from a buffer built only for the copy the buffer itself, a load of bytes only ever written with one constant each that constant, whatever the sizes of the stores, a slot stored once read as its value, a small structure split into its fields, the constants a slot can hold followed over the blocks), so a state kept in a local structure across a loop decides the branches on it; and, last before the moves are coalesced, `middle/passes/licm.c` makes what a loop computes the same on every trip once, in its preheader (the one block outside it that enters it and only jumps to its header): integer computations that cannot trap and read no memory -- constants, a global's address, arithmetic but division, shifts, masks; not compares, which branches read as flags, nor an index's scaling by 2, 4 or 8, which an address makes for nothing; a copy of a variable the loop does not write stays, and what is hoisted reads the variable instead (`copy_source()`), as the copy before the loop would be a second register held across it -- of operands defined only outside the loop, or by another such computation, made on every trip (in a block that dominates each jump back; a constant from anywhere), over the natural loops of the back edges innermost first, so that a matrix multiply's `&a[i][0]` leaves both loops inside the one over i; what two loops both made, now in one block, is then made once by `cse_function()`.

Technologies: C, SSA-style IR, verifier-driven invariants, simple optimization passes

Deployment: Shared between `cc` and standalone IR utilities (`ir-verifier`, `ir-normalize`, `ir-diff`)

### 3.4. Backend

Name: Instruction selection, register allocation, frame layout, and assembly emission

Description: The backend converts legalized IR into GAS-style assembly for supported ABIs. Before a function is emitted, x86-64's -mno-sse and -mno-sse2 refuse what cc can make with SSE only (`x86_check_sse_options()`: a float or a double returned, with gcc's error, and the other floats and doubles, which gcc makes on the x87), and -mno-80387 the x87's (`x86_check_x87_options()`). Before printing, branches are tidied (`tidy_branches()`), as copies gone have left blocks empty that were not at selection: a label nothing jumps to goes (none does in a function that takes a label's address), code after a jump or a return up to the next label, a jump or a branch to the label that comes next, and a branch over a jump is the one branch the other way; and a loop that tests at its top tests at its bottom too (`rotate_loops()`): the jump back to a test of a few compares, tests and copies and a branch is a copy of them and the branch the other way, into the body, so a trip takes one branch, not a jump and a branch.

Debug information (`-g`, `-gdwarf-4`, `-gdwarf-5`; `backend/dwarf.c`, `include/cc_dwarf.h`) is written as assembler directives at the end of the `.s`, as gcc writes it, and the assembler and linker turn it into bytes and relocations like any other data. Types come from the translation unit, which the module keeps (`cc_ssa_module_t.src_tu`): each declaration carries, beside its canonical type, the type as it spelled it (`frontend/dtype.c`, `include/cc_dtype.h`) -- typedef names, the enumeration a declaration named (whose canonical type is the integer type it is compatible with, the enumeration DIE's `DW_AT_type`), qualifiers on either, and the pointers, arrays and function types built on them; each such node knows the canonical type it stands for, and `cc_dt_fit()` keeps a spelling only where it still stands for the declaration's type (an array bound an initializer completed, say). Types are emitted on demand: a DIE naming one queues it, and only the types the unit's objects and functions reach are written; structure members get `DW_AT_data_bit_offset`/`DW_AT_bit_size` for bit-fields and `DW_AT_alignment` where gcc gives it (a type whose alignment the program asked for, which a structure takes from its members, gcc's TYPE_USER_ALIGN), so that pahole's layouts and BTF are gcc's. Functions: the backends tell the emitter where each starts and ends (`cc_dwarf_func_begin()`/`cc_dwarf_func_end()`, labels `.LdfbN`/`.LdfeN`, ranges in `.debug_rnglists`/`.debug_ranges` when they are in more than one section) and where each declared variable's stack slot is relative to the CFA (`cc_dwarf_func_slot()`: the slot layout's frame-pointer offsets, the machine IR's frame objects; none for an object the prologue realigns or a frame without a frame pointer). Lowering records each declared variable (`middle/dbgvar.c`, `cc_ssa_module_t.dbg_vars`) and marks the STACKALLOC that is its storage (`cc_ssa_instr_t.dbg_var`); a variable gets `DW_OP_fbreg` only when exactly one allocation of its own function, used by the code, carries its mark -- one the optimizer promoted, split or merged has no location, never a stale one. The calls each function makes before the middle passes (`cc_dwarf_note_calls()`) give the functions inlined into the code written, described as gcc's abstract instances with their variables, so that their types are the unit's too (Linux's tracepoint records). Line rows: lowering stamps each instruction with its statement's position (`cc_ir_set_pos()`, `cc_ssa_instr_t.dbg_line`, under -g only), the machine IR copies it (`xinst_t.dbg_line`), and each emitter prints a `.loc` where it changes (`cc_dwarf_loc()`), the first at the function's label with its name's line, so that a debugger's breakpoint on a function lands after the prologue has stored the parameters.

## 5. External Integrations / APIs

`as` and `ld`: The driver resolves sibling in-tree binaries first so host-native builds can exercise the full Substrate toolchain without installation.

Host preprocessor: Preprocessing support currently relies on a system `cpp` path for full macro/front-end coverage.

`--bootstrap-gcc`: A temporary compatibility path for source programs outside the currently supported native language slice.

Specifications: Functional requirements live in `SPEC.md`; capability/status notes live in `README.md`.

Tests: Compiler-facing regression surfaces live in `tests/usr.bin/cc/`.

## 6. Build, Installation & Invocation

Host/native mode: `make -C usr.bin/cc NATIVE_BUILD=1` builds `cc`, `cpp`, `ir-verifier`, `ir-normalize`, and `ir-diff` as host-runnable binaries.

Target mode: The default build links against Substrate CRT and libc and brands the output for the operating system image.

Build-mode isolation: `.build-mode` forces object and binary cleanup when switching between native and target builds so incompatible artifacts are not reused across modes.

Tool resolution order: environment override (`AS`, `LD`), sibling build-tree tool, same-directory tool, then PATH fallback.

## 7. Security Considerations

Recursive toolchain guard: The compiler participates in the same bounded toolchain-depth tracking as the assembler so shelling out across `cc`, `as`, and `ld` cannot recurse forever.

Preprocessor limits: Expansion depth, pass count, expanded text size, and expanded token count are bounded to cap hostile macro workloads.

Parser depth: Recursive parse depth is explicitly capped to prevent stack blowups from pathologically nested expressions or statements.

IR verification: Dedicated verifier utilities and legalization passes keep malformed or partially formed IR from silently reaching the backend.

Mode isolation: The `.build-mode` stamp prevents subtle native/target object reuse bugs, which are a correctness and diagnostic hazard during toolchain development.

## 8. Development & Testing Environment

Local build: `make -C usr.bin/cc NATIVE_BUILD=1`

Primary regression surface: `tests/usr.bin/cc/` contains positive/negative compile fixtures, conformance corpora, differential comparison suites, preprocessor mode scripts, ABI mode matrices, and IR verifier fixtures.

Standalone tools: `ir-verifier`, `ir-normalize`, and `ir-diff` make IR regressions easier to isolate than end-to-end compile failures alone.

Integration role: The compiler is the coordinator for real-world toolchain tests because it drives `as` and `ld` together on larger inputs.

## 9. Future Considerations / Roadmap

Structure: the refactor of the compiler as a whole is done -- one type representation, a typed AST from sema, one constant evaluator, a typed target-neutral IR with the ABI and legalization per target, thin emitters, and a compiler that builds itself (`run_selfhost.sh`).  Left from it: per-compilation state is still file-scope variables -- the interned type table (`frontend/ctype.c`), the language, target and settings (`common/lang.c`, `common/target.c`, `common/options.c`), and diagnostics' file names and label serials (`frontend/preproc.c`, `frontend/parser.c`, `frontend/sema.c`, `backend/x86/common.c`) -- where one context passed through the phases would let a process compile more than once.  A third target is possible and not scheduled.

Correctness: gcc (or clang, for the clang-compatibility tests) is the judge; a program cc compiles differently is a bug, fixed with a test under `tests/usr.bin/cc/` that fails before the fix.
